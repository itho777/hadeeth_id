# Two server-side changes that could not be deployed from this repo

## 1. Instant answers on the Razi bridge

`assets/data/razi_seeds.json` holds twenty reviewed answers — the ten starter
questions the web widget and the mobile card show, in ID and EN — each written
against a row read from `cdn.hadeeth.id` (reference, grade and wording taken
from that row). They are NOT model output: an earlier batch generated by Razi
answered a hadith question with Qur'an verses and was discarded. Tapping one of
those questions in the mobile app answers from that asset without a network call.

For the same instant behaviour on **web**, deploy `tool/razi_seed_cache.js`
into the Worker that serves `/api/chat`, with `tool/seed_answers.json` beside
it. It matches on normalised question + language and returns the prepared reply
before the model session starts; everything else falls through to the existing
handler. The endpoint remains unchanged for clients.

The Worker source itself is not in `G:\hadeeth_id` (that repo only contains the
browser-side `js/razi-chat.js` widget), so this could not be deployed here.
The file is written against the standard Cloudflare Worker `fetch` signature —
if the live Worker uses a different entry point, only the import/wrapper line
needs adapting.

Regenerate the asset after editing the questions (offline; the answers are
authored in the script itself, one slot per question and language):

```sh
python tool/gen_prepared_answers.py
```

`tool/gen_razi_seeds.py` is the old generator that asked Razi live; it is kept
only for reference and must not be used to produce shipped answers.

## 2. Supabase account sync

The Supabase project in `G:\hadeeth_id\js\config.js` is live, but all candidate
tables (`profiles`, `bookmarks`, `reading_progress`, …) returned **404** through
PostgREST, and that file's `ANON_KEY` is a truncated placeholder. So neither
web nor mobile currently has anywhere to sync bookmarks or last-read data.

Run `tool/supabase_user_sync.sql` in the Supabase SQL editor. It creates the
three tables, row-level security scoped to `auth.uid()`, and a profile trigger
for new users. Then:

1. Restore the full anon key in `js/config.js` (web) — it is public by design.
2. Add email/password + Google provider in Supabase Auth and set the redirect
   URLs for `hadeeth.id` and the app's Android deep link.
3. Wire `supabase_flutter` into the mobile app and upsert `bookmarks` /
   `reading_progress` from the existing `AppState` data. Until step 1–3 are
   done, the profile page deliberately keeps everything local instead of
   showing a sign-in button that cannot succeed.
